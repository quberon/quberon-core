  401, not 500). Stored values are built independently with hashlib/base64 at
  low round counts, so algorithm/encoding/field-order changes are caught.

STILL NOT TRUE:
- verify_password does NOT validate the scheme prefix: the first $-field is
  discarded (stored.split("$", 3) unpack), so any/empty prefix verifies if
  rounds/salt/key match. Pinned as a characterization test
  (test_verify_password_ignores_scheme_prefix_characterization), not endorsed.
  Fixing it in app/main.py is outside this node's owned paths.
- verify_password imposes no upper bound on the stored rounds value it will
  honour; a stored value with an enormous round count would make PBKDF2 run
  that long. Not tested (would hang the suite). Stored hashes are normally
  server-generated by hash_password (fixed 260000), so reachability depends
  on an attacker writing the users table - not assessed here.
- int(rounds) accepts forms hash_password never emits (e.g. " 1000 ", "+1000");
  observed in probing, deliberately not pinned as a contract.
- No timing / constant-time claim: hmac.compare_digest is used for the key
  comparison, but these tests assert results only, never latency or timing.
